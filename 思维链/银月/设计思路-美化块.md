# 银月 · 美化块：设计思路与取舍

> 这份文档解释 `silver-moon-blocks-inline.js` / `silver-moon-blocks-class.js`
> 是怎么想出来的、为什么这么写、哪些地方故意没做。
> 当前版本 **v1.3**。配套：`README-美化块.md` 讲怎么装怎么用，本文讲「为什么」。
>
> 环境事实（核对过）：SillyTavern 1.14.0 + 酒馆助手(JS-Slash-Runner) 4.9.3；
> 你的设置里 `streaming_fps = 55`、`encode_tags = false`、

---

## 0. 一句话

原来那 9 条美化正则之所以臃肿，根子在**酒馆会把自定义标签整段删掉**，
所以「块与块的分界」在 DOM 里活不下来，只能用一条巨型否定预查正则在文本层面
硬啃。现在改成：**用一条几十字符的标记正则把分界标进 DOM，剩下所有事由银月脚本在渲染后做。**

---

## 1. 起点：正则到底臃肿在哪

不是「正则」这个工具的问题，是三个具体的痛点：

1. **01-小左 那条是防御性解析**。它的内容是
   `(?:^|\n)[ \t]*(?:<thinking_left>\s*)?((?:(?!<\/?thinking_left>|<content>|…)[\s\S])+?)\s*<\/thinking_left>`
   —— 可选开标签 + 一大串否定预查（不许跨过任何别的标签）。之所以要这样，
   是因为模型有时漏开标签、有时漏闭标签，而**文本层面没有「块」的概念**，
   只能靠「下一个已知标签」当边界。改一个标签名，就得把这条长正则里所有分支同步改一遍。
2. **12 份文件、12 处重复的 HTML/CSS**。配色、字号、圆角散在 12 个 `replaceString` 里，
   想统一调一次要改 12 处；`trimStrings`/`placement`/`markdownOnly` 这些元数据也要各写一遍。
3. **能力和正则绑定**。「01 到 05 是折叠块、06 是药丸、07 是右对齐落款、08 只脱壳、12 是变量块」——
   这些差异只能靠「一条正则配一个静态 replaceString」表达；想加个「流式时展开」这种事，
   正则根本表达不了。

所以目标不是「把正则写短」，而是**把美化这件事从文本替换搬到 DOM 装配**，
正则只保留它最擅长的那一小块：**做词法标记**。

## 2. 摸清的硬约束（这决定了整个方案）

写代码之前我读了 ST 的 `public/script.js`、正则扩展 `engine.js`、
酒馆助手的 `dist/@types.txt` 与打包产物，确认了四件事：

### 2.1 显示管线的顺序（`messageFormatting`）

```
消息文本
  → substituteParams（宏）
  → getRegexedString(…, isMarkdown: true)    ← 显示类正则在这里跑
  → fixMarkdown / encode_tags（转义 < >）
  → converter.makeHtml（showdown，不是 marked）
  → DOMPurify.sanitize
  → 浏览器解析器把它塞进 .mes_text
```

两个直接结论：

* **正则跑在 showdown 和 DOMPurify 之前**，所以正则产出的 `<details style=…>` 能活下来；
* **展示用的正则必须是 `markdownOnly`（destination.display / 不含 prompt）**，
  否则同样的替换会跑进提示词，把上下文污染成 HTML。

### 2.2 自定义标签会被 DOMPurify 整段删掉

`DOMPurify.sanitize` 用的是默认允许列表（只额外 `ADD_TAGS: ['custom-style']`）。
`<thinking_left>` 这类不在列表里 → **元素被删掉、文字留下来**。
于是渲染后的 DOM 里，`<thinking_left>AAA</thinking_left><thinking_right>BBB</thinking_right>`
看起来就是 `AAABBB` —— **分界丢了**。

这正是 01 那条巨型正则存在的根本原因：它必须在文本阶段（标签还在的时候）就完成切分。

### 2.3 流式期间整条消息会被重排

`updateMessageBlock()` 里是 `messageElement('.mes_text').html(messageFormatting(...))`，
也就是**每次 token 批次都把 `.mes_text` 整个重建**，频率 ≈ `streaming_fps`（你这里 55 次/秒）。
这带来两个后果：

* 想在流式期间美化，就得**每次重排之后重新装配**；
* 装配必须赶在**这一帧绘制之前**完成，否则会闪（见第 5 节）。

### 2.4 另外两条不能碰的线

* **09-剧情选项**：它的 replaceString 是一段 ` ```html <body>…` 前端代码块，
  由酒馆助手渲染成 iframe（`StreamingIframe` / srcdoc），里面的脚本用 `window.parent` 往输入框填字。
  自己造 iframe 很难做到像素级一致，而且这条链路跟「文本 → 标签」是两回事 → **保持原样**。
* **10 / 10b / 11**：`promptOnly` 的上下文精简正则，作用在提示词侧 → **完全不动**。

## 3. 三条路，为什么选「一条标记正则」

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 纯 JS 逐字符映射 | 拿原始文本的区域，去 DOM 里按字符对齐（小cot 里 `findCotRanges` 那套） | 不用正则，但要对齐 showdown 做过的引号/链接/强调/宏替换，代码量翻几倍且遇到链接、`**加粗**`、宏替换就错位。**脆** |
| B. JS 自动注册原正则 | 脚本把 9 条正则生成好再写回酒馆正则表 | 输出 100% 一致，但正则还是那 9 条，只是从别处生成；「臃肿」没解决，还要动你的设置。**没意义** |
| C. 一条标记正则 + DOM 装配 | 标记正则只把 `<tag>` 换成位置标记，样式与结构全由脚本决定 | 分界能穿过 DOMPurify；解析逻辑用 JS 写（清晰、可扩展）；换标签/配色只改一张表。**选它** |

选 C 的代价是：**酒馆正则列表里仍然会多一条**。但那条是：

```
查找：/<(\/?)(thinking_left|thinking_right|thinking_love|thinking_director|inner|time|elapsed|content|UpdateVariable)>/g
替换：<span data-sm="$1$2"></span>
作用范围：AI 输出   仅格式显示（markdownOnly）
```

几十个字符，**不含任何样式、不含任何 HTML 结构**，纯位置标记。
它由脚本自动装卸（`ensureMarkerRegex` / `removeMarkerRegex`），
你不需要手写；它改名/删除会让美化失效（脚本会提示）。

> 顺带一个设计决定：`choice` **不在**标记正则里。
> 因为 09 那条正则要用原始 `<choice>` 标签；如果被我们先换成 `<span>`，09 就匹配不上了。

## 4. 装配算法：从标记到区块

核心函数是 `processContainer(container, streaming)`。流程：

### 4.1 配对（`collectMarkers` + `pairMarkers`）

* 扫 `container.querySelectorAll('span[data-sm]')`（文档序天然有序）；
* 开标记进栈、闭标记与最近的同类开标记配对；
* **处理顺序：后出现的 open 先处理**（`b.open.index - a.open.index`）。
  这样内层先装好，外层提取区域时会把已装好的内层块一起搬进去，天然得到「嵌套块」；
* 有闭无开的情况单独收集（`orphanCloses`）——这是 01 那条「可选开标签」容错的对应实现：
  只处理 `optionalOpen` 的标签（目前只有 `thinking_left`），从上一个标记之后一直捡到闭标记。

### 4.2 提取区域（`Range.extractContents`）

```js
range.setStart(pointBefore(openMarker));
range.setEnd(pointAfter(closeMarker));
const frag = range.extractContents();
```

用 Range 而不是手工 splice 节点，是因为它能跨 `<p>`/`<li>`/`<pre>` 等任意层级，
边界落在文本节点中间时会自动克隆半边，不需要自己处理。

### 4.3 裁剪（等价于原正则里的 `\s*`）

原正则写的是 `<tag>\s*(内容)\s*</tag>`；标记正则不删任何字符，所以那些换行会在
showdown 里变成 `<br>`。因此要在 fragment 上把首尾的空白/`<br>`/`<p>` 内首尾空白都剥掉
（`trimEdges` / `trimEdgesEnd`，递归到 4 层），才能和原来「视觉一致」。

`06-时空栏` 原来还允许内容外面包 `` ` `` 或 ` ``` `（在 DOM 里成了 `<code>`/`<pre><code>`），
所以 `unwrapCodeWrap()` 负责把这类壳剥成纯文本。

### 4.4 外壳

变体 A（内联版）的外壳字符串是**从原 replaceString 抄下来的**，一字不差：

```js
'<details style="margin:6px 0;border-left:3px solid ' + spec.color + ';background:' + spec.bg + ';…">' +
  '<summary style="…">' + spec.label + '</summary>' +
  '<div style="padding:2px 12px 10px;font-size:13px;line-height:1.75;white-space:pre-wrap;opacity:0.88;"></div>' +
'</details>'
```

变体 B（类名版）把同样的声明搬进一份 CSS，**CSS 由 BLOCKS 表生成**：

```js
out.push('#chat .mes_text .sm-details{margin:6px 0;border-radius:0 8px 8px 0;}');
BLOCKS.forEach(b => {
  var scope = '#chat .mes_text [data-sm-tag="' + b.tag + '"]';
  out.push(scope + '{border-left:3px solid ' + b.color + ';background:' + b.bg + ';}');
  out.push(scope + ' > .sm-summary{color:' + b.color + ';}');
});
```

于是「改一次配色」两种情况都只改 BLOCKS 表一处。
（注意 B 里没有用 `!important`：内联样式在原来也没有 `!important`，
所以不加才和原行为等价。）

### 4.5 三个「解析器补偿」

这三处是调试过程中真正花时间的地方，也是「外观一致」的关键：

1. **段落顶开**（`hoistOutOfParagraph`）
   原方案里正则产出 `<p>…<details>…</details>…</p>`，浏览器的 HTML 解析器遇到
   `<details>` 会把 `<p>` 顶开（块级元素闭合 p）。我们在 DOM 里插节点不会触发这个规则，
   所以自己把段落切成两半（`before` / `after` 两个克隆），把块放到中间。
   *只处理直接挂在 `.mes_text` 下的 `<p>`*，避免把嵌套块（外层块的正文容器）拽出来。

2. **列表抬升**（`hoistOutOfList`）
   块内容是 markdown 列表时，模型常写成
   `… 列表最后一项\n</thinking_left>\n<thinking_right>\n…`，
   showdown 会把后面的标签内容**吸进最后那个 `<li>`**。于是块被放进列表项里，
   浏览器会给它画一个列表编号（就是你截图里那个「孤零零的 1.」）。
   处理：装配完后统一再抬一次——如果某个 `<li>` 里只剩我们这个块、而且整条列表只剩这一项，
   就把块提到列表外面，并把空列表删掉（`pruneBlankListShells`）。

3. **空列表外壳**（`pruneBlankListShells`）
   提取内容后会残留 `<ol><li><p></p></li></ol>` 这种空壳。
   **空列表项照样会画出编号**，这就是那个「1.」的直接来源。
   每趟装配收尾时清一遍。

### 4.6 幂等：签名

`processContainer` 装配完会在 `.mes_text` 上写：

```js
container.setAttribute(DONE_ATTR, MARKER_SIG + ':' + hashText(消息原文));
```

下次扫描**先比签名，没变就直接返回**。这样：

* 重复扫描不会重复装配（对照台里有「重复 scan 幂等」断言）；
* 没有 CoT 标签的楼层也会被记上签名，第二次直接跳过（这条是性能的关键，见第 6 节）；
* `MARKER_SIG` 里带版本号，改了装配逻辑或标记正则就整体重装一遍
  （`ensureMarkerRegex` 写成功后会调 `clearDoneMarks()`）。

## 5. 流式：怎么做到不闪

### 5.1 我第一版写错了

v1.2 我用 `setTimeout(…, 0)` 排装配。问题是**定时器是宏任务**，
浏览器完全可能在「酒馆重排完成」和「我的定时器执行」之间先绘制一帧 ——
那一帧画出来的是没装配的原始文本（标签已被删，只剩正文）。55 次/秒重排 → 你看到闪。

### 5.2 正确做法：在 MutationObserver 回调里同步装配

MutationObserver 的回调是**微任务**：它在「当前任务（酒馆的 innerHTML 重排）」
结束后立刻执行，**而浏览器的绘制发生在微任务队列清空之后**。
所以在回调里装配，块和重排会出现在**同一帧**里，中间那点原始文本没有任何机会被画出来。

实现：`runStreamPassSync()`（在 observer 里直接调，不经定时器）。

对照台里我加了机制断言来证明这一点——**模拟酒馆重排后只让微任务跑，一个定时器都不许跑**：

```
PASS  不闪：酒馆重排后、下一个宏任务之前就已经装好
      <{"assembledBeforeTimer":true,"leftoverMarkers":0,"openDetails":1}>
```

### 5.3 还没闭合的块

流式期间经常出现「只有 `<thinking_left>`、还没有 `</thinking_left>`」。做法是：
**最后一个标记如果是未配对的 open，就把这块一路装到消息末尾**；
闭合标签到了，下一趟会重装成正常块。这样块是「跟着文字长出来的」。

### 5.4 展开策略（`streamingOpen`）

* `'partial'`（默认）：正在写的那块展开，你能看着它长；**已经写完的自动收起**成折叠头；
* `'all'`：流式期间全展开（跟你没装脚本前一样能读全文），生成结束一起收起；
* `'none'`：都不展开，只看折叠头。

生成结束后（`endGeneration`）走一趟普通扫描：如果酒馆在结束时重排过，块本来就会重建；
如果没重排，`closeStreamedBlocks()` 兜底把标题匹配我们 BLOCKS 表的 `<details>` 收起来。

### 5.5 跟不动怎么办

单趟同步装配耗时超过 `streamSlowMs`（默认 12ms，长消息/慢机器），
就把 `streamSyncOk` 置 false，本轮改用 120ms 节流兜底（会略微牺牲跟手程度，但不会占满主线程）；
下一轮生成（`noteActivity` 检测到「从非生成变成生成」）自动恢复同步。

## 6. 性能：为什么不会随楼层数变慢

### 6.1 原来的问题

第一版是「任何 DOM 变动 → 全聊天扫一遍」，而且每条消息都要
`document.querySelector('#chat #curEditTextarea')` 查一次编辑状态。
楼层一多，这两件事都是 O(楼层数)。

### 6.2 现在的四层防护

1. **签名快路**（`processContainer` 开头）
   没变的楼层只花「一次属性比较 + 一次文本哈希」，**完全不碰 DOM**
   （`collectMarkers` 的 `querySelectorAll` 才是贵的）。
   文本直接读 `window.chat[id].mes`（`getRawMessageText` 把这条放在最前面，
   不再走酒馆助手 API 的对象构造）。
2. **只扫变动的楼层**（`startObserver` + `messageElementOf`）
   observer 挂在 `#chat` 上；回调里从 `mutation.target` 找到它所属的 `.mes`，
   只处理那一两层（`scheduleMessages`），不再全扫。
   只有「整块换掉」（换聊天、加载更多）才退化成全扫。
3. **全扫按时间分片**（`runScanChunk`）
   一次最多占主线程 `scanBudgetMs`（默认 8ms），剩下的用 `setTimeout(0)` 挪到下一帧。
   几百层聊天在加载/切换时不会卡一下。
4. **流式只碰最后一层**（`getLastMessageElement`，从列表末尾往前找），
   而且热路径里连签名都不算（算了也用不上）。

### 6.3 实测（jsdom 跑的，它的 DOM 比真浏览器慢不少，看量级）

85 层楼层、其中 40 层带 CoT 块：

| 场景 | 耗时 |
|---|---|
| 首次全扫（要装配 40 层） | 合计 181ms，**切成 ≤14ms 一片**，一帧一片 |
| 第二次全扫（签名命中、全跳过） | **3.0ms** ≈ 0.04ms/层 |
| 单层变动（内容没变 → 跳过） | 1.4ms / 0.7ms（几乎全是调试接口那次 `querySelector`） |
| 单趟流式装配 | **1.87ms**（每帧预算 16ms，够用） |

## 7. 边界：哪些不碰、哪些会打架

| 对象 | 处理 |
|---|---|
| 09-剧情选项 | 不动。它靠酒馆助手的「前端代码块 → iframe」渲染，点击要往输入框填字 |
| 10 / 10b / 11 | 不动。提示词侧的上下文精简 |
| **酒馆助手 → 允许流式渲染** | **别开**。开了之后流式期间显示的是酒馆助手自己复制的那份 DOM（`.mes_streaming`），本脚本美化的是 `.mes_text`，两边对不上 → 流式期间看不到块 |
| 用户设置 → 编码标签（`encode_tags`） | 必须关。开着的话消息里的 `< >` 会被转义，正则产出的 HTML（原来的也一样）会变成字面文本。脚本启动时读 `#encode_tags` 复选框并提示 |
| 原来的 9 条正则 | 脚本不会偷偷删。启动时检测「还在启用且命中我们管的标签」的正则，在控制台提示；`migrate()` 一键停用（只改 `enabled`，`unmigrate()` 可还原） |

  + 一条「漏开标签」容错样本 + 一条**切在 `<thinking_right>` 中间**的流式样本；

* 类名版：CSS 声明与现状内联样式**逐条对齐**（各 49 条，无缺无多），

## 9. 踩过的坑（都是这套验证抓出来的）

1. **`data-data-sm-tag`**：类名版 CSS 选择器我多拼了一个 `data-`，
   于是配色规则整条不生效。被「CSS 声明逐条比对」当场抓住 ——
   有意思的是「声明集合」是齐的（49=49），只有「按标签配对」那条断言炸了。
2. **孤零零的「1.」**（就是你截图那个）：空 `<ol><li>` 残留。见 4.5-3。
3. **块被卷进列表项**：见 4.5-2。
4. **会闪**：`setTimeout` vs 微任务。见第 5 节。
5. **高楼层全扫**：见第 6 节。
6. **测试自身的两个坑**（值得一提，因为差点误导我）：
   对照台为了比对会把所有 `<details>` 强制展开，导致「流式展开态」断言读错；
   性能测试里的全扫又会把流式展开态收起来（真实场景里生成期间不会跑全扫）——
   最后是把「性能测试 → 流式测试 → 不闪测试」排成串行链才稳定。

## 10. 已知差异与取舍（故意不改 / 故意改了）

**故意不改的**：装饰、配色、标签文案、圆角、字号、行高、透明度、区块结构、
`pre-wrap` 的换行行为 —— 全部与原内联样式逐条对齐。

**明知不一样、但没去复刻的**：

1. 现状里浏览器解析器会在块与块之间留下几个空 `<p></p>`，每个多出 10px 空隙；
   新方案没有这些空段落（顶层换成裸的 `<br>` + 换行，排布与现状一致）。
   这些空段落在现状里是解析器的副产物，去复刻它属于复刻 bug。
2. **块内容是 markdown 列表时**：现状那 9 条正则会**把第一项退化成字面文字 `1. `**
   （正则产出的 HTML 和 `1.` 挤在同一行，showdown 认不出列表），后面几项才是列表。
   新方案渲染成**完整的真列表**（编号由浏览器画，缩进悬挂都正常）。
   这一点是变好了，所以我没改回去；如果你更想要「和现状一模一样」的退化成字面编号，
   说一声，加个开关就行。

**一个边角**：生成中如果**卡住超过 `idleFallbackMs`（默认 12s）**没有任何 token，
脚本会当作「生成结束」收尾一次（期间展开的块会收起）；
下一个 token 到达时会重新回到流式装配。想更宽容就把这个值调大。

## 11. 可配置项一览（两个版本相同）

| 键 | 默认 | 作用 |
|---|---|---|
| `manageMarkerRegex` | `true` | 是否自动装卸那条标记正则 |
| `markerScope` | `'global'` | 标记正则放全局 / `'preset'` / `'character'` |
| `markerScriptName` | `'银月 · 美化标记（勿删）'` | 在酒馆正则列表里的名字 |
| `debounceMs` | `180` | 生成结束后的装配延迟 |
| `streamingRender` | `true` | 流式期间是否装配 |
| `streamingThrottleMs` | `0` | 0 = 每次重排后在同一个微任务里装好；吃 CPU 就调 60~150 |
| `streamSlowMs` | `12` | 单趟超过它就本轮改用节流兜底 |
| `streamingOpen` | `'partial'` | 流式期间展开策略：`'partial'` / `'all'` / `'none'` |
| `scanBudgetMs` | `8` | 全扫每帧最多占主线程多少毫秒 |
| `idleFallbackMs` | `12000` | 生成中断的兜底判定 |
| `initDelays` | `[0,300,900,1800,3600,7000,12000]` | 启动补渲染时刻 |
| `verbose` | `false` | 控制台多说一点 |
| `BLOCKS`（不是 CONFIG，是表） | — | 标签 / 类型 / 文案 / 主色 / 背景色，改这里等于改全部 |

调试接口（控制台）：

```js
__silverMoonBlocksInline.version / .status() / .scan() / .process(mesid, {streaming:true})
__silverMoonBlocksInline.markerRegex        // 打印那条标记正则（自动装失败时手动建用）
__silverMoonBlocksInline.migrate() / .unmigrate()
__silverMoonBlocksInline.installMarkerRegex() / .uninstallMarkerRegex()
```

## 12. 附录：本地对照台怎么跑

```powershell
# 起一个只读的静态服务器（工作区根目录，仅监听 127.0.0.1:8791）
node .work\serve.js
# 浏览器打开
#   http://127.0.0.1:8791/.work/harness/harness.html            （内联版）
#   http://127.0.0.1:8791/.work/harness/harness.html?variant=class （类名版）
```

页面里三栏对照 + 一份文字报告（含结构/文字/声明比对）与性能数字。
`.work/` 是临时目录，看完可以直接删；`harness/sample-shot.txt` 是你截图那条真实消息，
留着以后回归用。

命令行版（我平时用的，带 35~60 条断言）：

```powershell
node .work\jsdom-run.js "思维链\银月\silver-moon-blocks-inline.js" .work\report.txt
node .work\jsdom-run.js "思维链\银月\silver-moon-blocks-class.js"  .work\report-class.txt
```

> 注意：jsdom 不在工作区里（我当时装在系统临时目录），
> 换机器跑要先 `npm install jsdom`。浏览器那版（harness.html）不依赖 jsdom。
