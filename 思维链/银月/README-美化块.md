# 银月 · 美化块（把 01~08、12 那 9 条美化正则搬到脚本里）

当前版本 **v1.3**（查版本：控制台 `__silverMoonBlocksInline.version`）

对应脚本（**只装一个**）：

| 文件 | 说明 |
|---|---|
| `silver-moon-blocks-inline.js` | 变体 A：生成**和原来正则逐字一致**的 HTML（样式写在元素内联 style 上） |
| `silver-moon-blocks-class.js` | 变体 B：外观一样，但样式抽成一份 CSS，元素上只留类名 + `data-sm-tag` |

两个变体除了「样式放在哪」以外完全一样，已逐条比对过（见文末「验证」）。同时装两个会重复装配，脚本启动时会互相告警。

对应关系：

```
01-小左        02-小右        03-小爱        04-前额叶
05-内心活动    06-时空栏      07-时间结算    08-正文去壳    12-隐藏变量更新
```

**不动**：`09-剧情选项`（靠酒馆助手的前端代码块 → iframe 渲染，点击要填输入框）、
`10 / 10b / 11`（提示词侧的精简正则）。

## 1. 为什么需要一条「标记正则」

自定义标签 `<thinking_left>` 这种在酒馆渲染时会被 DOMPurify **整段删掉**（只留正文），
于是「块和块的分界」在 DOM 里就丢了 —— 这正是原来 `01-小左` 那条嵌套否定预查正则存在的原因。

脚本的做法：

1. 自动往「酒馆正则」里装**一条极简标记正则**（就几十个字符，不含样式、不含 HTML），
   唯一作用是把标签换成位置标记：

   ```
   查找正则：  /<(\/?)(thinking_left|thinking_right|thinking_love|thinking_director|inner|time|elapsed|content|UpdateVariable)>/g
   替换为：    <span data-sm="$1$2"></span>
   作用范围：  AI 输出      勾选「仅格式显示」（markdownOnly）
   ```

   它在酒馆的显示流程里跑，分界因此能穿过 DOMPurify 活到 DOM 里；**提示词侧不受影响**。

2. 消息渲染完成后，脚本按标记把每一块装配成原来的美化 HTML。

> 这条标记正则会以「银月 · 美化标记（勿删）」的名字出现在酒馆正则列表里。
> 名字别改，删了美化就失效（改 `CONFIG.markerScriptName` 后同步改名也行）。

## 2. 安装（3 步）

1. **酒馆助手 → 脚本库 → 新建脚本**，把 `silver-moon-blocks-inline.js`（或 `-class.js`）整份粘进去，保存并启用。
2. **刷新酒馆页面**。脚本会自动装好那条标记正则，并开始装配美化块。
3. **让旧正则让位**：把 `01~08`、`12` 这 9 条正则禁用或删除。
   懒得分的话，在 F12 控制台执行一次：

   ```js
   __silverMoonBlocksInline.migrate()      // 类名版用 __silverMoonBlocksClass
   ```

   `migrate()` 只是把命中这些标签的正则 `enabled = false`，随时可以：

   ```js
   __silverMoonBlocksInline.unmigrate()    // 还原
   ```

   `09 / 10 / 10b / 11` 不会被碰（提示词正则、以及 09 那条都不在命中范围里）。

> 就算忘了禁用旧正则也不会重复渲染：旧正则先跑就把标签吃掉了，脚本找不到标记 → 什么都不做，
> 只是回到旧外观；脚本启动时会检测并在控制台提醒还剩几条。

## 3. 回滚 / 卸载

| 想做的事 | 怎么做 |
|---|---|
| 只停用脚本 | 在脚本库里关掉它，刷新即可（旧正则还在的话就回到旧外观） |
| 连标记正则一起清掉 | 控制台 `__silverMoonBlocksInline.uninstallMarkerRegex()` |
| 重新装标记正则 | 控制台 `__silverMoonBlocksInline.installMarkerRegex()` |
| 完全不想要了 | 删掉脚本条目 + 删掉「银月 · 美化标记（勿删）」这条正则 |

标记正则写进的是**全局正则**（`CONFIG.markerScope` 可改成 `'preset'` / `'character'`）。
如果你的 01~08、12 是装在预设里的，改成 `markerScope: 'preset'` 更一致（放全局也能用）。

## 4. 流式输出时也渲染（v1.2 起默认开）

酒馆流式输出时是**每次重排整条消息**（`.mes_text` 整个重建，频率 = 用户设置里的
`streaming_fps`，你现在是 55 次/秒）。所以脚本改成：每次重排之后就装一遍。

* **正在写的那一块会展开**，你能看着它一行行长出来；已经写完的块自动收起成折叠头。
  生成结束后所有块回到默认折叠态（和原来完全一样）。
* `CONFIG.streamingOpen` 可改：`'partial'`（默认，只展开正在写的那块）/
  `'all'`（流式期间全部展开，跟你没装脚本前一样能读全文）/ `'none'`（流式期间也不展开）。
* `CONFIG.streamingThrottleMs` 默认 `0` = 每次重排后在**同一个微任务里**装好
  （原始文本没有机会被画出来）；觉得吃 CPU 可以调 60~150。
* 想彻底关掉流式装配就设 `streamingRender: false`，那就回到「生成完才出现块」的老行为。

> ⚠️ **别开酒馆助手的「允许流式渲染」**（酒馆助手 → 渲染设置里那一项，你现在是关的）。
> 开了之后流式期间显示的是酒馆助手自己复制的那份 DOM（`.mes_streaming`），
> 本脚本美化的是 `.mes_text`，两边对不上，流式期间就看不到美化块了。

## 5. 性能（高楼层）与「不闪」

### 5.1 不会随楼层数变大而变慢

四层防护：

1. **签名快路**：每条消息装配完会在 `.mes_text` 上写一个签名（消息文本的哈希）。
   之后扫描先比签名，没变就直接跳过——只花一次属性比较 + 一次哈希，**不碰 DOM**。
   所以「已经装好的楼层」几乎不花钱。
2. **只扫变动的楼层**：DOM 变动不再全聊天扫，而是从变动节点找到它所属的楼层，
   只处理那一两层。
3. **全扫按时间分片**：`scanBudgetMs`（默认 8ms）一片，剩下的挪到下一帧继续；
   几百层的聊天在加载/切换时不会卡那一下。
4. **流式只碰最后一层**，而且热路径里连签名都不算、也不遍历整屏找「最后一条」。

实测（在 jsdom 里跑的，它的 DOM 操作比真浏览器慢不少，看相对量级即可；
85 层楼层、其中 40 层带 CoT 块）：

| 场景 | 耗时 |
|---|---|
| 首次全扫（要装配 40 层） | 合计 136ms，但被切成 ≤14ms 一片，一帧一片 |
| 第二次全扫（签名命中、全部跳过） | 3.5ms ≈ 0.04ms/层 |
| 单层变动（内容没变 → 跳过） | 0.7 ~ 1.3ms（几乎全是调试接口那次查询的开销） |
| 单趟流式装配 | 1.7ms（要挤进每帧 16ms 预算，够用） |

流式那趟若单趟超过 `streamSlowMs`（默认 12ms，长消息或慢机器），会自动改用
120ms 节流兜底，不硬扛着占满主线程；下一轮生成时自动恢复同步跟。

### 5.2 为什么不闪

关键在**同步**：装配是在 MutationObserver 回调里直接做的。那是**微任务**，
跑在浏览器「这一帧绘制」之前——所以装好的块和酒馆的重排出现在同一帧里，
中间那点原始文本根本没机会被画出来。（早先用 `setTimeout` 时就会闪：
定时器可能落在绘制之后。）

对照台里有一条自动验证：模拟酒馆重排后**只让微任务跑、一个定时器都不许跑**，
断言块已经装好 ✓。

如果实机还是觉得跟得太紧（CPU 吃得多），调 `streamingThrottleMs` 到 60~150，
或者 `streamingRender: false` 彻底关掉流式装配。

## 6. 想改东西改哪里

两个脚本顶上都是同一张表，改它就等于改全部：

```js
var BLOCKS = [
  { tag: 'thinking_left', kind: 'details', label: '小左 · 记忆与逻辑', color: '#5b9bd5', bg: '#5b9bd514', optionalOpen: true },
  ...
];
```

* `label` 折叠栏文字、`color` 主色、`bg` 背景色（8 位十六进制，末两位是透明度）
* 变体 A：内联样式由这张表生成；变体 B：CSS 由这张表生成（`--` 不用手写两份）
* 其它可调项：`debounceMs`（装配延迟）、`idleFallbackMs`（生成结束兜底判定）、
  `initDelays`（启动补渲染时刻）、`manageMarkerRegex`（是否自动装卸标记正则）、
  `verbose`（控制台多说一点）

## 8. 验证做到了哪一步

用 jsdom 搭了一个 A/B 对照台（真实 showdown + DOMPurify，复刻酒馆的
`正则 → showdown → DOMPurify` 流程），左边是现状（9 条正则），右边是新脚本。
样本包括 4 条消息，其中一条是真实长消息（四个思考块 + 时空栏 + 正文 + 剧情选项，
块内容是 markdown 列表）。

* 文字无增无减（抹掉空白与字面列表编号后与现状一致）
* 没有残留标记 `<span data-sm>`、没有裸露的自定义标签
* 块外壳数量一致、顶层节点序列基本一一对应
* 没有空的列表外壳（不会多画出孤零零的编号）、块不会被卷进列表项里
* 流式装配（把一条真实消息切在 `<thinking_right>` 中间当样本）：正在写的那块**展开**、
  已写完的块**收起**、没有残留标记、内容没丢、块没被卷进列表项
* 重复 `scan()` 幂等（不会重复装配）
* 类名版：CSS 里的声明与现状内联样式**完全对齐**（各 49 条，无缺无多），
  逐个标签的边框色/背景色/标题色/描边色都对得上

**两处已知差别**：

1. 现状里浏览器解析器会在块与块之间留下几个空 `<p></p>`，每个多出 10px 空隙；
   新方案没有这些空段落（顶层换成裸的 `<br>` + 换行，排布与现状一致）。
2. 块内容是 markdown 列表时，现状那 9 条正则会把**第一项**退化成字面文字
   `1. `（因为正则产出的 HTML 和 `1.` 挤在同一行，showdown 认不出列表），
   新方案渲染成**真正的列表**（编号由浏览器画，缩进/悬挂对齐都正常）。
   装饰、配色、标签文字、圆角、字号、行高、透明度仍是逐条对齐的。
