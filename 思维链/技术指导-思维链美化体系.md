# 思维链美化 · 技术指导（维护者手册）

> 面向对象：下一个接手的人，或者下一个 AI。
> 读完应该能回答三件事：**这类东西该写在哪一层、为什么必须那么写、坏了去哪儿查**。
> 所有结论都带机制解释和证据位置（`文件` + 函数名，行号只作参考——版本一变行号就漂，**用函数名 grep**）。
>
> 覆盖的产物：`silver-moon.js`（银月）、`silver-moon-blocks-inline.js` / `zhinao.js`（美化块 A/B）、
> `小cot/cot-heart-soundV1|V2|V3.js`、`hs-danmaku.js`（弹幕）、`hs-blocks.js`（预设版美化块）、
> `regex-状态栏.json`（状态栏载荷）。
> 本文只讲**机制与纪律**，不涉及任何具体角色卡、聊天记录或单个实例的数据。

## 1. 一页看懂：五层分工

你这套东西不是"一堆正则"，是**五层分工**。判断一段新逻辑该写在哪里，先问：**它需要看到什么形态的文本？**

| 层 | 什么时候跑 | 看到的是什么 | 能干什么 | 现有产物 |
|---|---|---|---|---|
| **L0 提示词侧** | 发送前（`isPrompt`） | 即将进上下文的文本 | 精简、剥离、注入指令 | `10/10b/11`（`promptOnly` 精简正则）；弹幕那条把 `<zimu>…</zimu>` 整段删掉 |
| **L1 消息改写** | 收到/编辑消息时（**非** markdown、**非** prompt 那一趟） | 消息原文（标签还在） | **直接改 `message.mes`** | 银月两条归一化正则 + 写 `power_user.reasoning` |
| **L2 显示正则** | `messageFormatting`（`isMarkdown`） | 消息文本 | 文本 → HTML 片段 | 银月的「美化标记」、秋青那批美化正则、状态栏载荷、弹幕的 display 标记 |
| **L3 DOM 装配** | MutationObserver 回调（微任务） | 已经过 showdown + DOMPurify 的 DOM | 位置标记 → `<details>` 块 | 美化块 A/B、小cot V1/V2/V3、`hs-danmaku.js` |
| **L4 样式与容器** | 常驻 / 每消息 | —— | 主题、每消息一份的小应用 | 银月 `REASONING_CSS`；状态栏的每消息 iframe |

一条回复的完整数据流：

```
模型原文
  │
  ├─ L1 银月把 <think>/<thinking>/[思考]… 归一成 [metacognition]…</thinking>   ← 改的是 message.mes
  ├─ ST 的 parseReasoningFromString 按 power_user.reasoning 的 prefix/suffix 抽走 CoT
  │     → CoT 进 extra.reasoning，mes 只剩正文（此后显示侧再也看不到 wrapper）
  │
  ├─ L2 getRegexedString(mes, AI_OUTPUT, isMarkdown:true)
  │     标记正则把 <thinking_left> 换成 <span data-sm="thinking_left">
  │     状态栏正则注入它的 HTML 代码块
  │
  ├─ fixMarkdown / encode_tags → showdown(makeHtml) → DOMPurify.sanitize
  │     ⚠ 自定义标签在这一步被「删元素、留文字」
  │
  ├─ 浏览器把结果塞进 .mes_text
  ├─ L3 MutationObserver 回调（微任务，赶在本帧绘制前）按标记装配美化块
  └─ L4 主题 CSS 生效 / 状态栏 iframe 起自己的文档
```

证据：`.work/ref/st-mirror.js` 的 `receiveMessage()` 复刻的正是 L1 那一趟（先 `getRegexedString(mes, AI_OUTPUT, {})`，再 `parseReasoningFromString`，命中才 `message.mes = parsed.content`）；显示管线四阶段见 `设计思路-美化块.md` §2.1；执行顺序见第 2.5 条。

## 2. 不可违背的硬约束

下面每一条都是**踩过坑换来的**。违反它们不会当场报错，只会以"偶尔不对/偶尔闪/换台机器就坏"的形式出现。

### 2.1 显示类正则必须 `markdownOnly`

`markdownOnly = true`（`destination.display`）才会在 `isMarkdown` 那一趟跑。**不勾**它就等于同时作用在提示词上，把上下文污染成 HTML。

* 怎么写：酒馆正则里勾「仅格式显示」；酒馆助手 API 写 `markdownOnly: true, promptOnly: false`。
* 反面：`promptOnly`（L0）与显示正则**不许混**——同一段替换同时进提示词和显示，是最常见的一类污染。

### 2.2 自定义标签过 DOMPurify 会「删元素、留文字」→ 分界必须提前换成标记

DOMPurify 用默认白名单（额外只 `ADD_TAGS: ['custom-style']`）。`<thinking_left>` 不在白名单里 → **元素被删掉、里面的文字留下**。所以渲染后的 DOM 里

```
<thinking_left>AAA</thinking_left><thinking_right>BBB</thinking_right>
```

看起来就是 `AAABBB`：**分界丢了**。这就是原来 01 那条巨型正则存在的根本原因——它必须在**文本阶段**（标签还在时）就完成切分。

现在的标准做法（美化块 A/B、弹幕、预设版美化块都用它）：

```
标记正则（几十字符、只有位置、不含样式）：
  find    : /<(\/?)(thinking_left|thinking_right|…|UpdateVariable)>/g
  replace : <span data-sm="$1$2"></span>
  作用域  : AI 输出 + 仅格式显示
```

`<span>` 能活过 sanitize，于是分界进了 DOM，样式与结构全部由 L3 的脚本决定。

证据：`设计思路-美化块.md` §2.2；`silver-moon-blocks-inline.js` 的 `MARKER_RE` / `ensureMarkerRegex`；`hs-danmaku.js` 的 `zimu` 标记正则。

### 2.3 每批 token 都会整条重建 `.mes_text` → 装配只能"同步"做

ST 流式输出时是 `messageElement('.mes_text').innerHTML = messageFormatting(...)`，**每批 token 整条重建**，频率 ≈ `streaming_fps`（几十次/秒）。两个后果：

1. 想在流式期间美化，就得**每次重排之后重新装配**；
2. 装配必须赶在**这一帧绘制之前**完成，否则会闪。

**正确做法**：在 `MutationObserver` 回调里同步装配 —— 回调是**微任务**，跑在绘制之前。
**错误做法**：用 `setTimeout`（定时器可能落在绘制之后 → 裸文本先被画出来 → 闪）。这不是性能优化，是"不闪"的**必要条件**。

证据：`设计思路-美化块.md` §5.1–5.2（第一版就是 `setTimeout`，实测会闪）；`silver-moon-blocks-inline.js` 的 `startObserver` / `runStreamPassSync`；`hs-blocks.js` 头注释。

### 2.4 正则产出必须能活过 showdown + DOMPurify

正则跑在 showdown **之前**，所以能产出 `<details>/<span>/<style>`；但**产出的标签必须也在 DOMPurify 白名单里**。别指望自定义标签活下来，也别产出 `<script>`（会被 sanitize 掉；要跑 JS 得走酒馆助手的前端代码块那条路）。

### 2.5 执行顺序是 全局 → 预设 → 角色卡

`engine.js:11-16` 的 `SCRIPT_TYPES` 展开顺序 + `getRegexScripts()` 的 `[].concat(extension_settings.regex, preset_regexes, scoped_regexes)`（`.work/ref/st-mirror.js` 同款复刻）。它决定两件事：

* **正则该放哪层**：`markerScope: 'global'` 就比预设里的旧正则**先跑**；
* **谁先吃标签**：标记正则默认在全局，所以是**它先吃**，预设里的旧美化正则看到的是 `<span data-sm>`——于是不会双渲染（结论对，但理由和 `README-美化块.md` §2 写的相反，那处文档待订正）。

### 2.6 谁写 `power_user.reasoning`，谁决定 CoT 的归属

ST 原生 reasoning 解析只认**一对字面量** `prefix` / `suffix`（`auto_parse` 打开时）。这条链的关键时序：

```
收到消息 → L1 正则跑完 → parseReasoningFromString 抽 CoT 进 extra.reasoning → mes 只剩正文
```

后果：**显示侧（`markdownOnly` + `placement=[2]`）的正则再也看不到原始 wrapper**。所以：

* 想让"任何预设的开头 CoT 都变成一个块"，必须走 L1 改写 + 原生解析（银月这条路），**不能**靠显示侧美化；
* 反过来，一个针对原始 wrapper 的显示侧美化正则，在别人接管了 `reasoning` 之后就会**静默失效** —— 这就是「有时候缩不进去」这类反馈的系统性来源，不是某条正则写错；
* 银月为此做了两件事：探针（用 ST 自己的 `parseReasoningFromString` 验证这对 wrapper 真会被解析，不过就坚决不装）+ **让位**（别的启用正则也在管同一批标签时主动退让，而不是抢）。

### 2.7 大载荷必须整体待在一个围栏代码块里

状态栏那种几十 KB 的 HTML/JS 载荷，`replaceString` **必须**被 ` ``` ` 围栏整个包住。原因：没有围栏时 markdown 会按「缩进 ≥4 空格 = 代码块」的规则把它切碎，脚本尾部掉出代码块变成普通正文，交给酒馆助手渲染的前端就**不完整**。

实测（`.work/lz/pipeline.js`，复刻 ST 的 `messageFormatting` + `getRegexedString`，jsdom + showdown + DOMPurify，7 次取中位）：

| 版本 | 单条 文本→HTML | 结构 |
|---|---|---|
| **有围栏** | **15.4 ms** | **1 个 `<pre><code>`，整份 7.6 万字符都在里面** ✅ |
| 无围栏 | 24.7 ms | 2 个代码块 + 382 处 `&lt;`，只活下来 1 个 `<style>` + 1 个空壳 ❌ |
| 无围栏 + 逐条补丁 | 38.6 ms | 21 个代码块，结构更碎 ❌ |

## 4. 加一块新美化块的标准流程

以「加一个 `<battle_log>` 折叠块」为例，照下面 7 步做，不需要理解整个文件：

| 步 | 做什么 | 改哪里 |
|---|---|---|
| 1 | 定标签名（英文小写、唯一、不与已有标签前缀冲突） | —— |
| 2 | 进**块表**（唯一事实来源）：`{ tag: 'battle_log', kind: 'details', label: '战斗记录', color: '#c9a227', bg: '#c9a22714' }` | 变体 A/B 各一份 `BLOCKS`（两处必须一致） |
| 3 | 把 tag 加进**标记正则名单** | `MARKER_RE`（A/B 各一处）；改完记得升 `MARKER_SIG`（见步 6） |
| 4 | 提示词侧保证 AI 真会吐这个标签（预设里写清楚"用 `<battle_log>…</battle_log>` 包住"） | 预设文本，不是脚本 |
| 5 | 选外壳 + 裁剪：`details`/`inner`/`pill`/`footer`/`variable`/`unwrap`；裁剪用 `trimEdges`/`trimEdgesEnd`（等价原正则里的 `\s*`） | 装配段（`buildBlock` + 对应 `*Shell`） |
| 6 | 幂等：`MARKER_SIG` 变了会让**所有消息**重装一遍（写在 `data-sm-blocks` 里一起比对）——这是故意的，别绕过 | `MARKER_SIG` / `DONE_ATTR` |
| 7 | 加自检用例：正常块 / **流式切一半** / 块内容含列表 / 空块 / 重复 `scan()` 幂等 / 块在段落里与列表里 | `.work/harness` 对照台 + 对应自检台段落（第 8 章） |

`kind` 可选值（现成的 8 种）：`details`（可折叠，`optionalOpen` 控制默认展开）、`inner`（心里话，点击展开）、`pill`（行内小标，`unwrapCode` 去代码壳）、`footer`（页脚行）、`unwrap`（只去壳不留外壳，正文去壳用）、`variable`（变量更新块）。

**改外观**：只改 `BLOCKS` 表的 `label/color/bg`（`bg` 是 8 位十六进制，末两位是透明度）；变体 B 的 CSS 由这张表生成，所以不存在"改两处"的问题。

## 5. "改这里 / 别改这里"速查表

## 6. 排障手册（症状 → 定位路径）

先记**调试接口**：

| 产物 | 接口 |
|---|---|
| 银月 | `__silverMoon.status()`（含 `reasoning`/`normalize`/`conflicts`/`injectButton`/`owner`）、`__silverMoon.selfCheck()`、`retryInject()`、`takeOver()`、`refresh()`、`uninstall()`、`install()` |
| 美化块 A/B | `__silverMoonBlocksInline.status()` / `scan()` / `process(mesid)` / `markerRegex` / `migrate()` / `unmigrate()`（B 用 `__silverMoonBlocksClass`） |
| 小cot V3 | `__mayaCotV3Debug`（`scan()` 立刻重扫、`dispose()` 完整卸载；`separateHeart` 开关会写回脚本变量） |
| 弹幕 | `window.__hsDanmaku = { version, scan(), status(), dispose() }` |

| 症状 | 先看 | 再查 | 常见原因 |
|---|---|---|---|
| CoT 不进块，字面 wrapper 留在正文 | `__silverMoon.status().normalize.state` | 是不是 `probe-failed`/`yielded`/`off`？`conflicts` 里有谁？ | 探针没过（ST 不认这对 wrapper）；有别的正则也在管同一批标签 → 主动让位；功能被关 |
| 出现**两个**块 | `selfCheck().dom`（`bothInOneMessage`/`wrapperLeftInBody`） | 是不是消息自带 `reasoning`（ST 会跳过解析）→ 旧 wrapper 留在正文 | 预设自己也在插块；或多层美化同时生效 |
| 流式会闪 / 块等出完字才出现 | 美化块 `status()` 里流式是否开启 | `streamingRender`/`streamingThrottleMs`/`streamSlowMs`；是不是把装配挪进了 `setTimeout` | 违反第 2.3 条；或开了酒馆助手的「允许流式渲染」（那时显示的是它自己那份 DOM） |
| 高楼层卡 | 各脚本的扫描预算 | `scanBudgetMs`、是否每次全聊天扫、状态栏实例数 | 违反第 7 章；或每消息一份的大载荷实例太多 |
| 「缩不进去」且状态是 `installed` | `status().owner.mine`（多实例）、`resyncIfStripped` 有没有被触发 | L1 正则还在不在（酒馆正则列表里那两条「银月 · 思维链归一」） | 正则被别的实例/设置重载摘掉（自愈会补）；或同版本双实例抢归属 |
| 注入按钮点了没反应 | `status().injectButton.bound` | 酒馆助手是不是 4.11.3+；`getButtonEvent` 拿没拿到事件名 | 老版本没有那四个全局；或按钮是被别的实例写的 |
| 不知道"为什么让位了" | `__silverMoon.status().conflicts` | 冲突里那条正则的作用域与名字 | 设计行为，不是故障；要强制接管用 `takeOver()` |
| 状态栏不显示 / 显示成半截 | 导入进去的 `replaceString` 头尾是不是 ` ``` ` | markdown 是不是把它切成了多段代码块 | 违反第 2.7 条（少了围栏） |
| 换了新块但旧块还在 / 不更新 | 记忆属性 `data-sm-blocks` / `data-hs-done` 里的签名 | `MARKER_SIG` 变了没有 | 签名没升级，旧 DOM 被判定"已装配" |
| 两份实例互相拆 | `status().owner`（`mine`/`current`） | 是不是同时挂了脚本库一份 + 启动器一份 | 让位/归属协议；**只留一份**最省事 |
| 美化块整块消失、只剩正文 | 标记正则还在不在（酒馆正则列表里「银月 · 美化标记（勿删）」） | 是不是旧美化正则（01~08、12）又在跑 | 旧正则先把标签吃掉了（谁先吃取决于作用域，见第 2.5 条） |

> 通用第一招：**先看接口的 `status()`**，再决定查机制。这套脚本几乎每个都有状态快照，别靠肉眼猜。

## 7. 性能纪律

### 7.1 现成的四条防护（都在，别退回去）

1. **签名快路**：每条消息装配完在容器上写一个"文本哈希 + 版本"签名，下次扫描先比签名，命中直接跳过——**不碰 DOM**。所以"已经装好的楼层"几乎不花钱。
2. **只扫变动的楼层**：DOM 变动不再全聊天扫，而是从变动节点找到它所属的楼层，只处理那一两层。
3. **全扫按时间分片**：一次最多占主线程 `scanBudgetMs`（默认 8ms），剩下的挪到下一帧。
4. **流式只碰最后一层**：热路径里连签名都不算、也不遍历整屏找最后一条。

实测参考（jsdom，85 层其中 40 层带块）：首次全扫 136ms（切成 ≤14ms 一片）、二次全扫 3.5ms、单趟流式装配 1.7ms。

### 7.2 先量后改：正则 CPU 几乎永远不是瓶颈

对状态栏那种最"吓人"的写法实测：`findRegex` 的贪婪负向前瞻在最坏情况（407KB 消息）只要 **0.039ms**，700ms 轮询折算 ≈ 单核 1.1%。**所以"优化 findRegex / 换个写法"不会改善任何卡顿。** 先量，再改，别凭感觉重写正则。

### 7.3 GPU 侧开销在 headless 浏览器里量不出来

`backdrop-filter: blur()`、常驻 `will-change`、大量无限动画、`mix-blend-mode`、`feTurbulence` 噪声——这些是**合成/GPU 侧**成本。headless Chrome 跑 `--disable-gpu` 时它们几乎不体现，所以**不能**拿"跑分两版 FPS 差不多"当"优化无效"的证据。要验证得在真实浏览器里看 DevTools 的 Frame rendering stats 或录 Performance trace。

### 7.4 判断"真优化"的三条硬指标

1. **结构完整性**优先于耗时：载荷有没有被 markdown 切碎（代码块数量、`&lt;` 泄漏）。
2. **每实例成本**：动画条数、轮询间隔、监听器数量、prefetch 数量、CSS 体积。
3. **实例数**：同样的载荷，6 份和 200 份是两个世界。能靠 `maxDepth`/虚拟化减少实例数，收益大于继续抠单份。

> 顺带三条"每实例"级的老毛病（都还没修）：轮询不看 `document.hidden`、`precache` 没有跨实例去重、`document` 级监听每实例各绑一套。改这些的收益是**乘以实例数**的。

## 9. 版本与发布

1. **两套版本号**：脚本内部 `VERSION`（银月 1.4.x、美化块 1.3）与仓库发布号（`v2.x`）**不是一套**，历史上从不同步（发布 v2.0.1 里带的是银月 1.3）。改脚本行为 → 升脚本的 `VERSION`；对外发布 → 打仓库 tag。
2. **导入用的 json 必须与源码逐字一致**：`node .work\build-mingyue-json.js`（生成）+ `--verify`（8 个闸门：content 逐字一致、无 BOM、JSON 可来回解析、button 通道开着、`buttons` 为空、`export_with` 不变、`name/id/enabled` 不变、VERSION 跟随源码）。
3. **发布流程**：`git add` 只有成品 → commit（消息写清"症状 → 根因 → 修法"）→ `git tag -a vX.Y.Z -m …` → push main + tag → 建 Release（说明里带上"怎么升级"和 CDN 地址）。
4. **任何写 `settings.json` 的现场补丁必须先备份**（`.work/patch-live-mingyue.js` 就是这么干的），补完**回读校验**并留下还原命令。补丁是直接改文件，**要在酒馆刷新页面之前别让它保存设置**，否则会被内存里的旧内容覆盖。
5. 分发用 CDN 时，URL 里的 tag 就是版本；老 tag 永远指向老代码（`@v1.2.0` 那份就没有多实例归属逻辑，会和新的互拆）。
